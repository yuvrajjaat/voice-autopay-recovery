### The transcripts

Produced by the offline simulator, which drives the real `/tools/*` endpoints
with a deterministic decision engine in place of the voice model. They are
genuine runs of the backend — the same routes, guards and mock processor the
voice agent calls — but **they are not recordings of a live voice
conversation.** The screenshots above are from a live call; the text files in
`transcripts/` are not.

Regenerate them at any time:

```powershell
.\.venv\Scripts\python.exe scripts\simulate.py --save --reset
```

## The recommended three-scenario demonstration

Three conversations are enough to show the whole system. Each one demonstrates
something the others do not.

Before you start: open **http://127.0.0.1:8000/voice** in one window and
**http://127.0.0.1:8000/dashboard** in another, side by side. The dashboard
discovers the session the voice page creates and fills in the tool timeline as
you talk, which is the thing worth filming.

The postal code the agent asks for is in `data/customers.json`. It is
deliberately never sent to the browser, because it is the credential being
checked.

---

### 1. CUST-001 — successful payment recovery

**Postal code: 94107**

The headline path. Verify, explain, consent, retry, approved.

| Step | What to do | What to point out |
|---|---|---|
| 1 | Pick CUST-001, press **Start conversation**, press the widget's call button | The agent opens by saying it is automated and does not mention any amount |
| 2 | Say "yes, now is fine" | |
| 3 | Give the postal code when asked | The dashboard shows `payment_details_withheld` **before** this, then `identity_verified` after |
| 4 | Let the agent explain the failure | Forty-nine dollars, insufficient funds — read from the tool result, not invented |
| 5 | Say "yes, please try it again" | The agent asks permission before charging anything |
| 6 | Listen to the result | It reads back the real confirmation number, `C-0254` |

**Expected outcome:** `payment_recovered`. The ledger row for CUST-001 flips
from `failed` to `recovered` mid-call.

Transcript of the same flow offline: [`transcripts/cust-001.txt`](transcripts/cust-001.txt)

### 2. CUST-002 — payment link, and a refusal

**Postal code: 78702**

The most interesting of the three, because the agent has to say no twice.

| Step | What to do | What to point out |
|---|---|---|
| 1 | Pick CUST-002 and start the call | |
| 2 | Give the postal code | |
| 3 | Let the agent explain | The card has expired, so a retry **cannot** succeed — the backend says so with `retry_worth_attempting: false`, and the agent does not waste an attempt |
| 4 | Offer a different card: *"I have another card here, let me read you the number"* | **The agent must refuse.** It cannot take card numbers by voice. |
| 5 | Accept the link | |

**Expected outcome:** `payment_link_prepared`. Note the wording: the agent says
the link has been *put on the account*, not that a text or email was sent — the
backend returns `delivered: false` and the prompt forbids claiming otherwise.
The link points at `example.test`, a reserved TLD that can never resolve.

Transcript: [`transcripts/cust-002.txt`](transcripts/cust-002.txt)

---

### 3. CUST-006 — escalation

**Postal code: 55401**

What happens when nothing can be fixed on the call.

| Step | What to do | What to point out |
|---|---|---|
| 1 | Pick CUST-006 and start the call | |
| 2 | Give the postal code | |
| 3 | Let the agent explain | The bank reports the account behind the card is closed; `next_action` comes back as `escalate` |
| 4 | Ask for help / let the agent offer it | No retry is attempted at all — the dashboard shows `payment_retry_skipped` |
| 5 | Listen to the handoff | The agent gives a ticket reference and says a colleague **will call back**, never that it is transferring you now |

**Expected outcome:** `escalated`, with a `TCK-` reference on the session.

Transcript: [`transcripts/cust-006.txt`](transcripts/cust-006.txt)

## If you have time for a fourth

**CUST-010 — do not call.** Postal code 73102, but you will not need it: say
*"take me off your list"* at the opening. The agent honours it immediately,
with no pushback and **no retry attempted**, and logs `do_not_call`. That flag
is stored against the customer and outlives the call — it is what the dial
guard checks before any future outbound attempt.

Transcript: [`transcripts/cust-010.txt`](transcripts/cust-010.txt)

## After each call

Wait a few seconds and the dashboard should show **Call completed** with a
duration, and a final `voice_call_completed` row on the timeline. That is the
post-call webhook finalising the session. It needs
`ELEVENLABS_WEBHOOK_SECRET` configured; without it the endpoint returns 503
rather than trusting an unsigned payload.

To replay a scenario, press **Reset session** on the dashboard. That clears the
session's runtime state and the customer's ledger row, leaving
`data/customers.json` untouched — so the same scenario runs identically on the
next take.
